# Crates Agent Guide

`crates/` contains shared utility crates used across the workspace. Inspect the target crate's `Cargo.toml` before editing because Kaku keeps some WezTerm-derived crates and adds its own helpers over time.

## Scope

Key groups:

| Group | Crates |
|-------|--------|
| Terminal core | `codec`, `color-types`, `vtparse`, `wezterm-cell`, `wezterm-escape-parser`, `wezterm-surface` |
| GUI and input | `wezterm-font`, `wezterm-input-types`, `wezterm-gui-subcommands`, `wezterm-open-url`, `wezterm-toast-notification` |
| Mux, client, and remote | `wezterm-client`, `wezterm-mux-server-impl`, `wezterm-ssh`, `wezterm-uds`, `kaku-relay`, `kaku-remote` |
| Platform and process | `pty`, `filedescriptor`, `procinfo`, `env-bootstrap`, `umask`, `async_ossl` |
| Lua and config support | `luahelper`, `wezterm-dynamic` |
| Shared utilities | `promise`, `base91`, `bidi`, `bintree`, `frecency`, `lfucache`, `rangeset`, `ratelim`, `tabout`, `wezterm-blob-leases`, `wezterm-char-props`, `wezterm-version` |
| Kaku-specific utilities | `kaku-ai-utils`, `kaku-unicode-names` (generated Unicode name table lifted out of `kaku-gui/src`; regenerate with `ucd-generate`, do not hand-edit) |

## Practical Rules

- For macOS notification actions that launch Kaku commands, prefer resolving bundled executables relative to the running `kaku-gui` binary.
- Keep `kaku-ai-utils` provider-agnostic; provider policy belongs in GUI/CLI call sites and config, not in low-level helpers.
- When shared cache helpers affect startup, verify the GUI consumer and avoid invalidating hot-path caches unnecessarily.

## Web Terminal and Relay

`kaku-remote` serves a browser terminal (`src/web.rs`, page in `assets/web/`) and `kaku-relay` lets it be reached from outside the LAN (`src/share.rs` on the Mac side). Both ship only with the `remote` cargo feature. Invariants:

- Not launched: the maintainer uses it privately until deciding to open it up. Release and Nightly builds leave the `remote` feature off, `kaku remote` is hidden from `--help`, and no doc, README, menu, setting, release note or issue reply mentions it. Build it locally with `CARGO_FEATURES=remote ./scripts/build.sh`; a signed, notarized copy for handing to friends comes from `./scripts/nightly.sh --private`, which writes `dist/private/Kaku-private-<sha>.dmg` and stops before anything touches GitHub. `nightly.sh` refuses `remote` in `--features` otherwise, crate-qualified (`kaku/remote`) included, and `release.sh` unsets an inherited `CARGO_FEATURES` before building. Both publish paths run `scripts/check_no_web_terminal.sh`, which greps every binary in `Contents/MacOS` (the CLI too) of the app and the mounted DMG for strings only `crates/kaku-remote` contains, so a private build left in `dist/` cannot go out through `--upload-only` or a release.
- Off until the user turns it on (2026-10-16): `remote.enabled` defaults to false. `kaku remote` asks before turning it on and writes `config.remote = { enabled = true }` to the user's kaku.lua through the settings screen's line writer (`config_tui::set_remote_enabled`); `kaku remote off` writes false. Neither rewrites a `config.remote` table that holds other keys (a relay of their own), which a whole-line rewrite would drop; they say to edit it instead. The bridge follows config reloads (`follow_config`): it starts when the setting turns on, without restarting Kaku, and when it turns off its runtime is dropped, which ends the relay link and every web session within a second, and the state file is removed so `kaku remote` no longer sees sharing. Turning it on again in the same Kaku works; checked by toggling twice in an isolated app.
- No LAN access (2026-10-16 decision, replacing the 2026-10-15 opt-in): the local server listens on 127.0.0.1 only and `remote.bind` is deprecated and ignored, kept so configs that set it still load. The maintainer has no use for it at home and it was plain HTTP: `http://192.168.x.x` is not a secure context, so `crypto.subtle` is missing (measured in Helium), and the relay's https page cannot open a `ws://` LAN socket (mixed content). Do not bring LAN access back.
- The local server answers only requests whose `Host` is its own (`127.0.0.1`, `localhost` or `[::1]` with the listener's own port, so a config reload that edits `remote.port` does not lock the page out), so a web page that rebinds its name to 127.0.0.1 cannot read same-origin responses. No route serves the token: `kaku remote` reads it from the 0600 state file. The routes for the old iOS client (`/api/config`, `/api/panes`, `/qr` with the token, `/ws/{pane_id}`, and the `ai_chat` handler in `kaku-gui/src/ai_remote.rs`) were removed on 2026-10-14 with the maintainer's approval: its relay mode had already stopped working, and `/qr` handed the token to any local process, other macOS users included. A future iOS app should speak the web terminal's protocol or wrap the page, not bring these back.
- A session ends after `SESSION_SILENCE` (180 s) without a message from its browser, so a half-open socket from a sleeping laptop does not hold App Nap off forever.
- One session per browser, carried either by the local WebSocket (`#t=<token>` link) or by the relay (a paired browser, see below). `run_session` only sees two string channels; keep transport logic out of it.
- The page mirrors Kaku's own terminal model as ANSI frames rather than replaying the PTY stream, so terminal queries are answered once, by Kaku. Keys go through `Pane::key_down`, pastes through `send_paste`.
- Anything that reads the Lua config (for example `can_close_without_prompting`) must run on the GUI thread via `promise::spawn::spawn_into_main_thread`; calling it from the server's tokio threads panics.
- Relay ids are the first 128 bits of SHA-256 of a secret that never leaves the Mac, so nobody else can register as that Mac. Through the relay only paired browsers get a session (`src/pairing.rs`, 2026-10-15; the old `#k=<key>` link, one AES key for every browser, is retired and its pages are told to reload). `kaku remote` writes a one-time offer (`remote-pairing.json`, 10 minutes) and prints `/{id}/#p=<secret>&m=<Mac public key>`; the page makes a non-extractable ECDSA P-256 device key and keeps it in IndexedDB once Kaku has admitted it. Each connection: Kaku sends `KCH3` and an ephemeral P-256 key in the clear, the page answers `KCB3` and its own, both derive one AES-256-GCM key per direction by HKDF-SHA256 over the ECDH secret salted with the transcript (SHA-256 of `kaku-remote v3`, the relay id, both ephemeral keys). Kaku's first sealed message signs the transcript with its long-term key (`mac_key` in `remote-share.json`), which the page checks against the key from its pairing link before sending anything, so a relay cannot pose as the Mac; the page's first sealed message signs it with its device key (`auth`), adding an HMAC of the transcript under the offer secret the first time (`pair`). Messages carry their direction label and position as associated data. Close codes: 4403 not a paired browser (the page forgets its key), 4401 pairing link expired or used, 4426 page from before pairing, 4408 no proof in time; the relay must pass each through (`browser_close`), or the page reads it as busy and retries. Pairing shows no dialog, because the Mac is often unattended when a browser is added from elsewhere: the link works once, every new device posts a macOS notification naming it, and so does a paired device connecting again after 30 minutes away (`QUIET_RETURN`; reloads and reconnects stay quiet), which is the Mac-side sign of remote use (no menubar or tab bar mark, by the maintainer's choice on 2026-10-15), and `kaku remote devices` / `kaku remote revoke <id>` list and remove devices (sessions of a removed device end within seconds). ring's ECDH takes only ephemeral keys, which is why long-term identity is a signature, not a static DH key; ring's fixed ECDSA signatures and WebCrypto's are the same r||s form.
- Each web session holds `awake::Awake`, a latency-critical `NSProcessInfo` activity. Without it, App Nap throttles the backgrounded GUI's main thread, which turns PTY output into the pane change the session renders from, and every echo waited 100-200 ms. Measure remote input latency with the Kaku window hidden, not focused.
- `Shown::update` turns a screen whose rows moved into `CSI n S` / `CSI n T` plus the new rows. That relies on each row starting with its own `CSI row;1H` and on the page never setting a scroll region; keep both, or the browser's copy drifts from Kaku's.
- Clipboard writes from programs (OSC 52, `MuxNotification::AssignClipboard`) also go to browsers viewing that pane (`web::publish_clipboard`, 1 MB cap); the Mac clipboard keeps getting them. Find (`Search`) runs on the Mac over the pane's history, so it reaches past what the page shows. Files a browser drops or pastes arrive in chunks, in a bounded window of eight 64 KB chunks, each acknowledged (`UploadAck`), so its percentage is what reached the Mac; a session that ends mid-file deletes the partial file (`Uploads` drop) and the page resends after reconnecting. Files are written to `~/Downloads/Kaku` under a sanitized, de-duplicated name (`safe_file_name`, `unused_path`, 50 MB cap), and their path is pasted into the original drop pane with `quote_dropped_files`, as a native drop would be.
- Scrolling a plain shell (`local_scroll` in each frame: no alternate screen, no mouse grab) never round-trips: the page fetches history rows with `History` in pages of `HISTORY_PAGE` and scrolls them in `#past`, laid exactly over the terminal with each run placed at Kaku's column. Programs that take the mouse or the alternate screen still get the scroll on the Mac, and Find still pins the Mac-side view (`View::pinned_top`).
- The page names tabs by `tab_id` and reorders them per `window_id`; rename and move go through `TabAction::Rename` / `TabAction::Move` in `kaku-gui/src/remote_tabs.rs`, which keep the Mac's active tab. A split tab lists its `panes`; viewing one sends `Activate`, which also focuses that split on the Mac, and `claim_tab_size` grows the tab by the split's share so the viewed pane gets the browser's grid.
- Web pane menus retain the selected `pane_id` through clipboard permission prompts and close dialogs. Splits call `Mux::split_pane` with that id rather than the deferred active-pane spawn path. Confirmed pane closes remove that exact pane, or record and remove its tab when it is last; `CloseCurrentPane { confirm: false }` is not sufficient under `AlwaysPrompt`. Middle-click tab close shares the existing browser confirmation path. Keep native phone selection menus intact.
- Web URL detection stops at CJK sentence punctuation and unmatched closing wrappers, retains balanced path parentheses, and maps UTF-16 regex offsets back to terminal cells, including surrogate pairs and wide end cells. The browser regression fixture includes the reported GitHub comment link followed by `)，并以`.
- A tab a browser sized keeps that size through relayouts the Mac does on its own (display or scale change, focus, config or theme reload, tab bar visibility): `apply_dimensions` asks `window_relayout_resizes_tab` per tab. Only the Mac's own use takes it back: typing or clicking (`reclaim_active_tab_size`) or a live window drag. Resizing it under the browser made Claude Code and Codex redraw for the Mac's rows and jump up in the page.
- The relay is public and sheds abuse itself: browser messages are capped at 512 KB and Mac messages at 4 MB; bytes queued toward one Mac (`HOST_QUEUE_BYTES`, the flooding browser is dropped) and toward one browser (`BROWSER_QUEUE_BYTES`, the stalled page is dropped) are bounded, and so are all queues together (`GLOBAL_QUEUE_BYTES`): a message count alone let one stalled page hold a gigabyte of 4 MB screens on a 256 MB machine. Every queue gives its unsent bytes back when its socket ends (`Queued`'s `Drop`), or the relay-wide budget leaks until nothing is accepted; at most 2 registrations per id (a third evicts the oldest) and 4 browser sockets per client address per host; hosts silent for 75 s and browsers for 150 s are closed. The relay serves the page and its files from its own copy, built in from `crates/kaku-remote/assets/web` and the two fonts (`page_file`), and asks no Mac for them; the page itself answers 404 with the offline notice while the Mac is away, which an open page relies on to tell an offline Mac from a network problem. So a relay deploy ships the page: deploy it together with Kakus that speak its protocol (pairing, `KCH3`), never ahead of them. `fly.toml` caps connections at 100 (soft 80), about 50 people online, which memory bounds rather than fly's proxy; raise it only with a load test or a larger machine, and the Docker build uses `Cargo.lock` with `--locked`.
- The page lives on its own origin, `t.kaku.fun` (2026-10-16), so serving a page that misuses the browser's keys takes a compromise of that origin, not just of the relay. `scripts/publish_web_page.sh` builds it from `crates/kaku-remote/assets/web` and the bundled JetBrains Mono, fills the `kaku-relay` meta tag (empty in the copies Kaku and the relay serve, which then talk to their own origin), writes a `vercel.json` with `/<id>` and `/<id>/` rewrites, a CSP that allows the one inline script by its SHA-256, and no caching, and deploys it with `vercel deploy --prod` to the `kaku-web` Vercel project, which holds nothing else: a path on `kaku.fun` would share an origin, and the keys, with every page of the site. The page must keep exactly one inline script and no inline event handlers, or the script refuses to publish. With `KAKU_RELAY_PAGE_ORIGIN` set, the relay 308s its page addresses there (the fragment survives), serves no page files, admits browser sockets only with that `Origin`, and answers `/<id>/status` (200 or 404, CORS for that origin) for the page's offline notice. Kaku links the default relay's page to `t.kaku.fun`, any other relay's to the relay itself. `crates/kaku-remote/tests/static_page.cjs` runs the published page behind a server applying its `vercel.json` and checks the redirect, pairing, bookmarks with and without the slash, a foreign `Origin` refused, and no CSP refusals; poll with `page.evaluate` there, since `waitForFunction` evaluates a string the CSP blocks. Publish the page before a relay deploy that sets the origin.
- The relay runs in `nrt` (Tokyo, `crates/kaku-relay/fly.toml`), the edge the Mac enters through: from `sin` every keystroke and echo crossed Tokyo to Singapore twice, 375 ms echo against 166 ms now. It keeps hosts in memory, so run one machine; two would split a Mac and its browsers across them.
- Only Mac-confirmed text is rendered. Cursor visibility cannot distinguish normal input from passwords, so never predict typed characters. Pages opt into a four-frame output window with `Hello.frame_ack`; ACK after xterm parses even an ignored pane frame, coalesce later dirty output, and leave legacy hello clients unthrottled.
- Browser selection copying follows the Mac's existing `copy_on_select` value and runs on selection release without a network hop. Preserve manual copy when disabled, reconstruct history line breaks and virtual gaps, and never queue a denied automatic copy for a later unrelated gesture. Browser clipboard permission and real mobile selection remain browser-specific.
- History keeps at most 10,000 row strings but materializes only visible rows and overscan, preserving stable DOM nodes that intersect an active selection. Cached tab attachment must precede resize, and an equal-size claim must still record browser ownership.
- Paths in the output (`~/…`, `/…`, `./…`, never inside a URL; `PATH_RE` in the page) are links: Cmd+click (Ctrl+click off the Mac) asks Kaku for that file (`Download`), and it comes back as a browser download. Kaku resolves `~` to the home folder and a relative path against the pane's working directory, sends only regular files up to 50 MB, and refuses folders and missing files by name. Chunks of 256 KB go out while less than `DOWNLOAD_WINDOW` (1 MB) is unacknowledged (`DownloadAck`), so the relay never holds much of a file for one browser; the relay drops a browser past 8 MB queued. A download ends with its session, and the page says so on a dropped link. Any paired browser already has the shell, so reading a file grants nothing new.
- Upload transfer ids bind the file and original pane for ten minutes after completion, across transport reconnects within the same app process. Retry returns the receipt without writing or pasting twice; cancellation and disconnect remove only partial files. Freeze the target once for a multi-file drop.
- Access code (2026-10-16, the launch gate the maintainer chose over trials): with `KAKU_RELAY_ACCESS_CODE` set (a fly secret the maintainer picks), the relay registers only Macs presenting it in `x-kaku-access`, compared as SHA-256 in constant time; 401 bodies say `access code required` or `wrong access code`, and ten wrong codes from one address lock it for `ACCESS_WINDOW` (429). `kaku remote` reads the relay status, asks for the code without echo when the relay refused it, saves it to `remote-access` (0600, ASCII only since it travels in a header), and waits for the bridge, which polls that file during its backoff and retries within a second. Every recorded attempt stamps `RelayStatus::checked`, so a second wrong code is told apart from a stale one. Per-address limits sit beside it: `CONNECTS_PER_MINUTE` new sockets and `MAX_HOSTS_PER_ADDR` registered Macs per `fly-client-ip`; local runs have no client address and are not limited. `live.cjs` runs its relay with a code and checks refusal, then acceptance after saving it.
- Registration tokens (`crates/kaku-relay/src/token.rs`) decide who may register a Mac: `base64url(claims).base64url(Ed25519 signature)` with `sub` (a relay id, or `*` for an invite), `kind` (`invite` now; `trial` and `pro` later) and `exp`. The relay holds only the public key (`KAKU_RELAY_TOKEN_KEY`, a fly secret) and checks offline; with `KAKU_RELAY_REQUIRE_TOKEN=1` a Mac without a valid token gets 401, otherwise every Mac registers as before and a bad token is only logged, so the key can be set before every Kaku carries a token. `kaku-relay keygen` prints a key pair and `kaku-relay issue [--host ID] [--kind K] [--days N]` signs with `KAKU_RELAY_SIGNING_KEY` from the environment; keep that key out of the repo and off disk. A Kaku keeps its token with `kaku remote --token <T>` (`remote-token`, 0600) and sends it as `x-kaku-token` on every registration. Tokens are short-lived and renewed by their issuer, so the relay needs no revocation list. The trial is planned to bind a token to the Mac's hardware id, not to an account.
- Every relay connect is capped by `CONNECT_TIMEOUT`: a local proxy (Stash TUN) can accept TCP and never finish the handshake, which once left the link offline for hours. Bound socket writes and session inbox waits too, but allow short input bursts to wait rather than discard keys. Wrong-key close 4403 is final; idle unauthenticated sessions expire with 4408. A host replacement closes browsers independently of the old data queue, with late input discarded until the close writer finishes.
- The private relay uses `r.kaku.fun` with `/{id}/` pages; `/t/{id}/` routes remain valid. Never shorten the 128-bit identity or put a pairing secret in a URL path/query. The page erases the fragment at once and saves the device only after Kaku admits it; when IndexedDB is unavailable it pairs for that tab only and says so. LAN tokens stay tab-only in sessionStorage. Explain pairing in the CLI and page messages, not public docs.
- One identity per Kaku, persisted at `DATA_DIR/remote-share.json` (0600), devices at `remote-devices.json`. `kaku remote --reset` replaces the identity and forgets every device; the running bridge notices within seconds and re-registers.

## Remote Verification

- For an authorized relay deployment, run `fly deploy . --config crates/kaku-relay/fly.toml --dockerfile crates/kaku-relay/Dockerfile --remote-only --depot=false --ha=false --strategy immediate` from the repository root (the build context must reach the page files; the root `.dockerignore` sends only what the relay embeds, about 1 MB, never `target/`). Use `--depot=false` when Depot stalls at builder authentication. Verify the Fly tunnel with `fly doctor` first; do not add `--wg=false` to a working tunnel, since the legacy builder's HTTPS path can fail with an h2c upgrade HTTP 500. This selects a build transport, not a system proxy setting. Verify the deployed image digest and an isolated encrypted session afterward; a dashboard without new releases does not diagnose a failure before image creation. If CLI DNS checks warn while HTTPS works, compare public DNS before changing anything.
- Run `cargo test --locked -p kaku-remote`, relay tests via its own manifest, and workspace check/tests/clippy with `kaku/remote,kaku-gui/remote` enabled. CI enables the feature only for tests and clippy, never for shipped packages.
- `node --test crates/kaku-remote/tests/web.test.cjs` uses Playwright Chromium to exercise the shipped HTML and xterm, including input privacy, reconnect, upload pacing, history selection, and viewport boundaries. Set `NODE_PATH` when Playwright is installed outside the checkout; `PLAYWRIGHT_CHROMIUM_EXECUTABLE` optionally selects an existing browser. The page draws with WebGL when it can, so most tests launch with WebGL off and read the DOM fallback, and one test checks the WebGL grid, down to its text pixels. CI's Chromium has no WebGL2 and skips that test, so run the suite locally with a browser that reaches the real GPU: on the maintainer's Mac that is Helium (`PLAYWRIGHT_CHROMIUM_EXECUTABLE=/Applications/Helium.app/Contents/MacOS/Helium`, headless on Metal). Playwright's own Chromium downloads fail code signing on Darwin 27 and its headless shell only has SwiftShader, whose WebGL timings are meaningless. Never emulate `deviceScaleFactor` for WebGL checks or measurements: it changes `devicePixelRatio` but not `devicePixelContentBoxSize`, so xterm sizes its canvas at half the device size and draws nothing or a shrunken grid, a failure real browsers do not have.
- `node crates/kaku-remote/tests/static_page.cjs` (same app and relay setup as `live.cjs`) launches its browser with `--disable-gpu`: headless Helium on Metal stops opening new tabs once a page drew with WebGL (navigations abort before any request reaches the server, `newPage` hangs), which looked like a page bug for two rounds.
- After a private `make app` with `CARGO_FEATURES=remote` and a debug relay build, run `node crates/kaku-remote/tests/live.cjs`. It launches only its own app, temporary HOME, and loopback relay, tests encrypted input, uploads across reconnect, frame flow control, host replacement, stable split targets and AlwaysPrompt pane closing, foreign `Host` refusal, and replayed, misplaced and old-format messages, then removes its own fixtures. Never substitute a real share link.
